Cannamatrix platform architecture note

The noop reference pipelines: light and heavy

noop and noop_baked are diagnostic modules: they exercise the platform wiring without biological analysis. Light computes on the GitHub runner and stores an inline JSON result. Heavy computes on temporary EC2, writes the payload to S3, and has the GitHub runner store a pointer and summary in Supabase. Both share the job and artifact contract; heavy adds AWS authentication, SSM, storage checks, and cleanup.

How to read it. Figure 1 groups code by where it executes. Underlined paths inside the boxes open the corresponding source file or directory in a new tab. AWS resource names and machine-local paths are labeled separately. Use the arrow key for the operations; Figure 2 shows their ordering.

Key to Figure 1. Numbered relationships and the two alternative compute paths.
1The browser signs in through Supabase Auth. The login page calls signInWithPassword; the user session is carried by the browser. Unauthenticated visits to /dev/noop redirect to /login.
2The browser posts input_text to /api/noop/run (light) or /api/noop-baked/run (heavy), carrying the session cookie. The API also supports an optional own-org sample_id; the diagnostic page does not supply it.
3The shared handler calls getUser(), resolves membership from profiles joined to orgs, inserts an own-org queued job, and calls mint_job_callback_token. The job kind is noop or noop_baked. Mint checks the authenticated caller's org, returns plaintext, and stores only its hash and expiry (four-hour default).
4LDispatch noop.yml with job_id, callback_token, and input_text. The workflow supplies its default maturity=provisional.
4HDispatch noop-baked.yml with those three inputs plus server-derived org_slug and maturity=provisional. Both dispatches select GH_WORKFLOW_REF, falling back to platform-v2-modular. The server uses GITHUB_DISPATCH_TOKEN; the browser receives only { jobId } on success.
5LThe light runner calls record_job_started, runs noop.py, and uses post_artifact.py to call insert_job_artifact with inline JSON. It then attempts record_job_finished(done | failed). Callback writes use the Supabase anon key plus job token.
5HThe heavy runner first claims the job. Only a successful claim proceeds to AWS. After the S3 checks, it calls insert_job_artifact with a pointer envelope (schema_version, storage, outputs, summary), requests termination, and attempts record_job_finished with bounded retries. A successful finish clears the token hash and expiry.
H1Assume the AWS role with GitHub OIDC and launch EC2 using the launch template cmx-noop-baked-base. That template chooses the baked AMI and instance profile cannamatrix-genotype-runner. The runner retains the EC2 instance ID for SSM and cleanup. It later requests termination when an instance ID exists.
H2Wait for EC2 to be running and its SSM agent to be online. Send the input and science command through SSM, then poll get-command-invocation. Completion is observed through the SSM API; EC2 does not call GitHub back.
H3SSM runs /opt/cmx/noop_baked/science.py --in /tmp/nb_in.txt --out-s3 PREFIX --ran-on ec2. Input text is staged by the command. No Supabase callback token is sent to the instance.
H4The science process uses the instance profile to write result.json and result.json.meta under s3://cmx-tenant-<org_slug>-<account_id>/genotype-results/<job_id>/.
H5The runner verifies that both objects exist and are nonempty, reads the sidecar, validates its fields, and compares payload size with sidecar bytes. It copies the sidecar's SHA-256 into the pointer; it does not recompute the payload hash.
6–8After accepted dispatch, the browser refreshes immediately and then every ten seconds while waiting. The server reads the newest RLS-visible job across both noop kinds and its matching artifact, then renders the result card. This is not a browser-pinned job lookup. Polling stops on a terminal status or available artifact.

Two authorization paths. Job creation and result reads use the signed-in user's RLS context; mint is a SECURITY DEFINER function that checks the caller's organization. Runner lifecycle and artifact RPCs execute with owner privileges and validate the job token. The inspected noop flow uses no service-role API key. always() means cleanup is attempted when the workflow can run it; it does not guarantee that cleanup or the final RPC succeeds.

3Data modelentity–relationship

jobs.envelope in the drawing is shorthand for real metadata columns, not an actual column. Neither noop workflow populates jobs.instance_id, job-level S3 output fields, or cost fields. Heavy keeps its instance ID in workflow step outputs and stores the result pointer in job_artifacts.result. Both workflows record the GitHub run ID and lifecycle timestamps. The enum also contains reserved values dispatched, cancelled, and succeeded; these are not extra stages that noop traverses. Sources: jobs schema, artifact schema, status and policy notes.
