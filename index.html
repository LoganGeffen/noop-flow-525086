The noop reference pipelines — light and heavy

noop and noop_baked are the platform's two reference modules. Neither runs real science — each carries an input through the full pipeline and back so a returning card proves the wiring. Light (noop) computes inline on the GitHub runner and writes the result straight to Postgres. Heavy (noop_baked) runs on an ephemeral EC2, stores the payload in S3, and writes a pointer to it — the template every real EC2-scale module reuses. Both share the same rails, tables, and token-gated lifecycle below.

Reading the boxes. Each box shows its name, its [type], and a one-line purpose. The specifics — the secret it holds, its exact endpoints, and the repo file it lives in — sit in the components table under the figure; the numbered key decodes the arrows. Key to Figure 1. The shared flow (1–9) and the heavy branch (H1–H4).
1Member opens the plant or /dev/noop page. Not signed in, so they get bounced to /login.
2Login hits Supabase Auth (signInWithPassword for now, Globus later). It hands back a session JWT.
3Browser posts the input to /api/noop/run, carrying the session cookie.
4The route checks who you are, looks up your org with current_org_id(), and inserts a jobs row (kind=noop, status=queued) — all under your own row-level security.
5The route mints the job's callback token. It's returned once; Postgres keeps only its sha256 and an expiry.
6The route fires the workflow — noop.yml (light) or noop-baked.yml (heavy) — with the job id, token, input, and org_slug. This is the only step that holds GITHUB_DISPATCH_TOKEN.
7Light only. The runner runs noop.py, which builds result.json inline from the input; the runner then posts it to insert_job_artifact.
8The runner calls three RPCs in order — record_job_started, insert_job_artifact, record_job_finished — using the Supabase anon key plus the job token. The last call burns the token.
9The page polls: router.refresh() re-runs the server component, which reads jobs and job_artifacts under your row-level security. The browser never touches Postgres directly.
H1Heavy only. The runner assumes an AWS role by OIDC (no stored keys) and launches an ephemeral EC2 from the baked AMI cmx-noop-baked-base. The callback token is not passed to the box.
H2Over SSM the runner tells the box to run science.py, which writes result.json and a small result.json.meta sidecar to s3://cmx-tenant-…/genotype-results/<job>/ under the instance profile cannamatrix-genotype-runner.
H3The runner reads just the .meta and head-objects the payload to confirm its byte count matches, format-checks the sha256 and carries it into the pointer (it does not recompute the payload hash), then builds the S3-pointer envelope. It terminates the instance in an always() step.
H4The runner posts the pointer to insert_job_artifact (kind=noop_baked) — the same RPC as step 8 — so the two paths converge on one job_artifacts row shape.

Row-level security. Reads (4, 9) run under current_org_id(). The writes in step 8 are SECURITY DEFINER RPCs that bypass RLS — authorized by the per-job token and its expiry, not the user session. service_role never leaves Postgres.

The jobs.envelope row collapses the machine-written execution columns — instance_id, the S3 URI pointers, cost, error_class/detail, and the dispatch/start/finish timestamps. Light noop leaves the S3 and cost columns null; heavy noop_baked populates instance_id and the S3 pointer, the same columns a real EC2 module writes.
