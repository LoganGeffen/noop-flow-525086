Cannamatrix platform architecture note

The noop reference pipelines: light and heavy

noop and noop_baked are two test modules. Neither runs real science. Each one sends an input through the whole pipeline and back, so the result card at the end shows the plumbing works. Light (noop) runs on the GitHub runner and writes its result straight to Postgres. Heavy (noop_baked) runs on a temporary EC2 server, saves the output to S3, and stores a pointer to it. Real EC2-scale modules copy the heavy path. Both use the same steps, tables, and security.

How to read it. Each box lists its name, type, what it does, what it holds, and its file. Box color shows which system it belongs to (see the legend under Figure 1). Arrows show only a number; the key below explains each step. Thin grey arrows are internal steps. AWS parts live in AWS, not in the repo.

1System contextC4 · container

Key to Figure 1. Every arrow is just a number. This key explains each one. Shared flow 1 to 9, heavy branch H1 to H4. Each box’s own detail is printed inside the box.
1Member opens the plant or /dev/noop page. Not signed in, so they get bounced to /login.
2Login hits Supabase Auth (signInWithPassword for now, Globus later). It hands back a session JWT.
3Browser posts the input to /api/noop/run, carrying the session cookie.
4The route checks who you are, looks up your org with current_org_id(), and inserts a jobs row (kind=noop, status=queued). This runs under your own row-level security.
5The route mints the job's callback token. It's returned once; Postgres keeps only its sha256 and an expiry.
6The route fires the workflow, noop.yml for light or noop-baked.yml for heavy, with the job id, token, input, and org_slug. This is the only step that holds GITHUB_DISPATCH_TOKEN.
7Light only. The runner runs noop.py, which builds result.json inline from the input; the runner then posts it to insert_job_artifact.
8The runner calls three functions in order: record_job_started, insert_job_artifact, then record_job_finished. It uses the Supabase anon key plus the job token. The last call burns the token.
9The page polls: router.refresh() re-runs the server component, which reads jobs and job_artifacts under your row-level security. The browser never touches Postgres directly.
H1Heavy only. The runner assumes an AWS role by OIDC (no stored keys) and launches an ephemeral EC2 from the baked AMI cmx-noop-baked-base. The callback token is not passed to the box.
H2Over SSM the runner tells the box to run science.py. It writes result.json and a small result.json.meta file to s3://cmx-tenant-…/genotype-results/<job>/, using its instance profile cannamatrix-genotype-runner.
H3The runner reads the .meta file and checks the file in S3: it confirms the byte count matches and copies the sha256 into the pointer (it does not recompute the hash). It then writes the pointer and shuts the box down.
H4The runner posts the pointer to insert_job_artifact (kind=noop_baked), the same function as step 8. Both paths end at one job_artifacts row.

Row-level security. Reads (steps 4 and 9) run as the signed-in user's org. The writes in step 8 use SECURITY DEFINER functions that skip row-level security. They are authorized by the per-job token, not the user session. The service_role key never leaves Postgres.

The jobs.envelope row stands in for the machine-written columns: instance_id, the S3 pointers, cost, the error fields, and the timestamps. Light noop leaves the S3 and cost columns empty. Heavy noop_baked fills in instance_id and the S3 pointer, the same columns a real EC2 module writes.
